## 一、先直接回答你的两个问题

**① 有没有成熟的客服插件能直接用？** 有，而且是成熟商业产品。但要把两件事分开：**「人工客服窗口」**和**「AI 知识库问答」**，前者早就成熟，后者是这几年才起来的。

**② 免费吗？** 分两层：

| 层次 | 免费情况 |
| --- | --- |
| 人工客服窗口 | **有真免费**：tawk.to 永久免费、不限座席与会话量（已核对官方 why-free 页面） |
| AI 知识库问答 | **基本没有长期免费的**：要么按月订阅，要么插件免费但**自备模型 Key、按 token 付费** |

所以严格回答：**"成熟 + 免费 + 能查知识库"的客服插件，不存在现成的免费午餐。** 免费的是座席，AI 的钱（订阅费或模型费）省不掉。唯一"接近零成本"的组合是 **tawk.to（纯人工，0 元）+ 开源 WP 插件自备 Key**。

## 三、本站特有的 4 个约束（这才是选型关键）

1. **前台是 Next.js 无头站**。WordPress 插件的聊天挂件默认只注入到 WP 自己渲染的页面，**不会出现在 3001 的前台站**。走 B 类插件就得手动把挂件脚本搬进 Next.js 的 layout，插件升级、脚本地址变化都可能让它失效。
2. **局域网演示**。SaaS 客服和云端大模型都依赖外网；若老板电脑或本机没外网，两者会同时失效，必须有"离线兜底"。
3. **C 盘只剩约 4 GB**。Docker + 镜像，或本地模型（Ollama 7B 量化约 4~5 GB）都装不下，走本地模型前必须先清盘。
4. **记录必须落在自己后台**。只有 B 类插件和路线 3 自建满足；A 类 SaaS 不满足。

另外，本项目已经有一批**能直接复用的资产**：123 款产品的结构化数据（编号 / 花色 / 色系 / 规格 / 耐磨层 / 性能 / 收边，存在 `_rc_payload`）、7 个空间的推荐花色名单、`rc_inquiry` 的询价后台范式（来源追踪 + 状态 + 备注 + CSV 导出）、`rococo/v1` REST 命名空间、前端已有的 Next 代理路由（`app/api/inquiry`）。**做 AI 客服所需的知识库和后端骨架，绝大部分数据已经躺在库里了。**

## 四、三条路线对比

### 路线 1：直接用 tawk.to（0 元，半天接入）

- 做法：注册 tawk.to → 拿 script → 加进 Next.js 的 `app/layout.tsx`（或对应语言布局）。
- 优点：成熟稳定、永久免费、不限座席、手机 App 就能收消息、不占本机资源。
- 缺点：**没有知识库 AI**（AI 要付费加购）；记录在 tawk 后台，不在 WordPress；依赖外网。
- 适合：只想先有个"能说话的窗口"，或作为 AI 上线前的过渡。

### 路线 2：WordPress AI 插件 + 自备模型 Key（约 1 天）

- 做法：装 AI Engine 或 Kognetiks Chatbot → 填模型 Key → 把产品数据喂进知识库 → 把挂件脚本搬进 Next.js。
- 优点：插件免费、**记录进 WordPress 后台**、自带知识库 / 嵌入能力、后台能看对话和"没答上来"的列表。
- 缺点：无头站要手工嵌脚本（升级有失效风险）；中文知识库抓取质量、回答质量需要实测；模型按 token 付费。
- 适合：想少写代码、且能接受"挂件脚本外挂在 Next.js 上"这种不够干净的接法。

### 路线 3：自建（**推荐**，约 3~4 天）

- 做法：前端做挂件（Next.js），后端挂在已有的 `rococo-core` 插件上，知识库用现有产品数据 + 人工 FAQ，模型走 API 或本地模型。
- 优点：**记录 100% 在自己的 WordPress 后台**、与现有询价后台同一套界面风格、不受插件升级影响、数据不外流、天然中英双语、可直接复用空间推荐与产品字段。
- 缺点：要写代码；需要定模型来源。
- 适合：你的原话——"**后台看对话 + 答不上来引导邮件**"——这正是 SaaS 做不到、插件型做得到但不够顺的部分，自建能做得最贴合。

**推荐结论**：若目标是"给老板长期用 + 后台看对话 + 答不上来引导邮件"，直接走**路线 3**；若只想要个立即可用的窗口，先上**路线 1** 兜底，路线 3 作为下一步；**路线 2 是不想写代码时的折中**。

### P6：验收清单

- 准备 20 条固定问题集：产品编号查询、花色 / 色系、耐磨层、规格、发货时间、运费、样品索取、退换、安装、保修，中英各半。

- 安全检查：浏览器端抓包看不到模型 Key；后台能看到完整会话；并发 / 连点不会打爆接口。

| 风险 | 说明 | 对策 |

## 八、附录：接口与数据结构草案

**接口**

```
POST /wp-json/rococo/v1/chat
请求: { session_id?, locale, message, page_url?, product_code? }
响应: { session_id, reply, answered, escalate?, refs: [产品编号...] }
```

`answered=false` 时，前端走 P4 的邮件兜底分支；`refs` 用于前端展示"相关产品"卡片（可选）。

**内容类型 `rc_chat` 的 meta**

| meta 键 | 含义 |
| --- | --- |
| `_rc_chat_messages` | 完整对话 JSON 数组（role / content / 时间） |
| `_rc_chat_locale` | zh / en |
| `_rc_chat_page` | 从哪个页面发起的 |
| `_rc_chat_status` | open / escalated / closed |
| `_rc_chat_email` | 兜底时客户留下的邮箱 |

**可选的后续增量**（本方案不含，供以后排期）

- 人工接管：AI 答不上来时转人工（那就需要接 B 类或 C 类方案）。
- 多轮上下文持久化、访客识别（复用现有 `session-tracker.tsx`）。
- 把常见问题反哺进 FAQ，形成"客服越用越准"的闭环。

## 九、跨站复用：能不能搬到另一个 WordPress 站？

**结论：能，但要看你用哪种"姿势"搭。** 这套东西里约 80% 与地板业务无关，可以原样搬；剩下 20% 是跟本站绑死的，必须改。**关键在于：有一个决策会提前决定"以后复用是 1 小时还是半天"。**

### 9.1 两类内容分清楚

| 完全通用（与业务无关，可原样搬） | 与本站强耦合（必须改） |
| --- | --- |
| 挂件 UI：气泡、对话框、流式输出、移动端全屏 | 品牌色、术语、系统提示词里的"ROCOCO 产品"措辞 |
| 后端代理层与 Key 保管方式（Key 只留服务端） | 知识库来源：本站从 `_rc_payload` 生成 `products.json` |
| 会话存储结构（CPT + 每轮消息 meta） | 数据接口：`rococo/v1` 命名空间与 products 端点 |
| 后台会话查看页 + CSV 导出 | 前端形态：本站是 Next.js 无头站 |
| 兜底逻辑：答不上来 → 留邮箱 → 标记「待跟进」 | 环境配置：`WORDPRESS_URL`、Key、兜底邮箱、语言 |
| 护栏：限流、限历史轮数、限输出长度 | 部署脚本 `install.ps1`（硬编码 `D:\WP\rococoeco`） |

### 9.2 一个必须先做的决策：用什么形态承载

**这是整件事的分水岭。**

| 承载形态 | 能复用到哪种站 | 每接一个新站要做什么 |
| --- | --- | --- |
| **Next.js 组件**（现在的写法） | 只能复用到**同样是 Next.js 无头**的站 | 复制组件 + 改 6 处硬编码，约半天 |
| **独立 WordPress 插件**（推荐） | **任何** WordPress 站：普通主题站、无头站都行 | 装插件 + 填 3 项设置，约 1 小时 |

原因很实在：普通 WordPress 主题站的页面是 PHP 渲染的，**Next.js 的 React 组件在那上面根本跑不起来**；反过来，插件可以靠 `wp_footer` 自动把挂件注入任何 WP 主题站，也能给无头站提供一套独立的 JS + REST。

**如果你确定以后要复用到别的 WordPress 站，就应该一开始就做成独立插件。** 这比先做进 `rococo-core`、以后再往外拆要省事得多——拆的时候要重写一遍接口、数据表和后台页。

### 9.3 推荐的复用架构：独立插件 + 双模式投放

新建插件 `site-chat`（不放进 `rococo-core`）：

| 部件 | 内容 | 通用化要点 |
| --- | --- | --- |
| 设置页 | 模型 Key、模型名、兜底邮箱、系统提示词、语言、限流阈值 | 全部存 `wp_options`，**不进 git** |
| 知识库加载 | ① 读取 `data/knowledge/*.json`（人工维护的 FAQ）② 从该站 WP 内容自动索引（可选文章 / 页面 / 自定义类型） | 本站的业务数据靠 ① 喂进去；别的站可以用 ② |
| `POST /site-chat/v1/chat` | 检索 → 调模型 → 返回，含兜底判定 | 独立命名空间，不依赖 `rococo/v1` |
| 会话存储 | CPT `aichat_session` + 每轮消息 meta | 与本站 `rc_chat` 结构一致，可参照 |
| 后台页 | 会话列表 + 详情 + 状态 + CSV 导出 | 完全通用 |
| **投放模式 1**（普通 WP 站） | `wp_footer` 自动注入挂件（原生 JS，无框架依赖） | 装完即用，无需改主题 |
| **投放模式 2**（无头站） | 输出独立 JS 挂件 + 上述 REST；前端任何框架都能接 | 本站走这一档 |

这样做完，**"换一个 WordPress 站"= 装插件 → 填 Key / 兜底邮箱 / 系统提示词 → 配知识库**，不用改任何代码。

### 9.4 移植清单（按"快但脏"的方式搬的话）

如果两个站结构几乎一样，也可以直接复制过去改这几处：

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | 后端接口文件 | 命名空间 `rococo/v1` → 该站自己的；知识库读取路径 |
| 2 | 内容类型注册 | `rc_chat` → 该站自己的前缀，避免和已有类型撞名 |
| 3 | 前台挂件组件 | 品牌色（改用 CSS 变量）、站名、中英文案 |
| 4 | 系统提示词 | 品牌名、产品品类、价格 / 交期口径 |
| 5 | 前端代理路由 | `WORDPRESS_URL` 指向新站（环境变量，通常不用改代码） |
| 6 | 部署脚本 | `install.ps1` 里的 `D:\WP\<站点>` 路径 |
| 7 | 知识库生成脚本 | 本站从 `_rc_payload` 生成；换站要换成该站的数据结构 |

每接一个新站约半天，且**两个站要各自维护一份代码——以后改 bug 得改两遍**。这就是推荐 9.3 的原因。

### 9.5 站点变多以后的升级路径

如果以后有三五个站都要这个客服，可以再走一步：**抽成中央服务**。

所有站的挂件都指向同一个 `/chat` 后端（只维护一份知识库、一个模型 Key、一个后台看板，会话集中可查）。代价是各站 WP 与中央服务之间要加一层**共享密钥**做鉴权，且中央服务要好维护（就是个常驻的小服务）。

建议顺序：**先做独立插件 → 站点多了再考虑中央化**。一开始就上中央服务属于过度设计。

### 9.6 复用带来的额外注意事项

| 事项 | 说明 |
| --- | --- |
| 模型 Key | 每个站一套 Key，或共用一套；**都只存服务端 / 插件设置里**，绝不能进前端代码或 git |
| 知识库隔离 | 每个站的知识库要各自独立，别把 A 站的产品答到 B 站去 |
| 后台分散 | 插件形态下，会话记录分散在各站自己的 WordPress 后台；想统一看就得上 9.5 的中央服务 |
| 成本合并 | 共用一套 Key 时，多站流量合并计费，记得设月度上限 |
| 版本一致性 | 插件要用版本号管理，否则"这个站修了、那个站没修"很容易发生 |

## 十、独立插件的技术选型（结论）

前提：目标是"**做一次，之后能装到别的 WordPress 站**"。下面 6 个决策点，每个都给出推荐与理由。

### 10.1 载体：自建独立插件，**不要 fork 现成插件**

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| 现成插件（AI Engine / Kognetiks）当载体 | ❌ | 数据表、挂件投放、后台页都在对方手里；跨站要复制它的表结构；插件升级会覆盖你的改动；闭源部分改不了 |
| fork 现成插件改成自己的 | ❌ | 上游升级断路、许可证有疑问、长期维护成本最高 |
| **自建独立插件** | ✅ **推荐** | 存储、挂件、后台、知识库全在自己手里；换站只填设置 |

> 现成插件可以**当参考**看：看它怎么切知识库、怎么设计后台会话列表。但别把它当骨架。

### 10.2 架构：插件当服务端，挂件只管展示

```
访客浏览器 → 挂件（纯展示）→ 本插件的 REST → 插件读知识库 + 调模型 → 返回
                                     ↑
                              Key、知识库、会话记录全在这一层
```

**Key 只存在于 WordPress 服务端**，前端永远拿不到。这是安全底线，也是以后换模型供应商时唯一要改的地方。

### 10.3 挂件投放：双模式一起做（这是"能跨站"的核心）

| 模式 | 适用站 | 做法 | 站点侧要改什么 |
| --- | --- | --- | --- |
| **模式 1** | 普通 WordPress 主题站 | `wp_footer` 自动注入挂件 | 什么都不用改，装完即用 |
| **模式 2** | 无头站（Next.js 等） | 输出独立 JS 挂件 + REST 接口 | 前端加一行脚本或一个组件 |
| 模式 3（附带） | 只想放某个页面 | 短代码 `[site_chat]` | 编辑页面时插入 |

两种模式**共用同一份挂件 JS 和同一套后端**，多做一种的边际成本很低。本站先走模式 2，别的站装完直接是模式 1。

### 10.4 知识库与检索：先规则、后向量（最关键的省钱点）

| 层级 | 做法 | 适用问题 | 成本 |
| --- | --- | --- | --- |
| **L1 结构化精确匹配** | 按产品编号 / 花色 / 色系 / 规格直接查字段 | "M0B68 是什么花色" | 近乎为零 |
| L2 关键词 / 全文匹配 | 用 meta 查询或自建一张索引表 | "有没有浅色木纹的" | 近乎为零 |
| L3 向量检索（RAG） | embedding + 余弦相似度 | 口语化、绕圈子的问法 | 多一个 embedding 接口的费用 |

**推荐先做 L1 + L2，够用就不上 L3。** 原因：地板官网这类问答里，"按编号 / 花色 / 规格查"占了绝大多数，**结构化匹配比向量更准、更便宜、还更好排查**。L3 解决的是口语化问法，属于体验优化，不是必需品。

**模型只负责组织语言，不负责瞎猜数据**——检索层把命中的产品记录塞进提示词，模型照着说。这一条能同时压住幻觉和成本。

若以后要上 L3：向量存在**自己建的一张 MySQL 表**里，PHP 侧算余弦相似度即可（几百到几千条数据完全够），**不要为此引入向量数据库**。

### 10.5 模型接入：走 OpenAI 兼容协议，别直连某一家

插件设置里做一层"供应商预设 + 自定义 baseURL"，内部统一按 OpenAI 兼容格式调用。好处是**换供应商只改两个字段**（baseURL + 模型名），不动业务代码。

| 场景 | 建议 |
| --- | --- |
| 中文站为主 | 国内模型的便宜档（DeepSeek / 通义 / 智谱等），延迟低、价格低、中文好 |
| 英文 / 多语种更看重 | OpenAI 小模型档或 Claude Haiku 档 |
| 完全无外网 | 需要"离线降级"开关：直接走留言 + 邮件，不假装能答 |

设置项至少要有：`baseURL`、`apiKey`、`model`、`temperature`、`maxTokens`、`月度调用上限`。

### 10.6 存储：会话一条 CPT，每轮消息一条 CPT

- **会话**：一条记录（标题 = 访客标识 + 时间），meta 存语言、来源页、状态、留存的邮箱。
- **每轮消息**：一条记录，用 `post_parent` 挂到会话上。

**不要把整段对话塞进一个 meta 字段**——meta 值会随对话变长而膨胀，后台详情页也会越来越慢。一对话一记录，列表好分页、导出也好做。

会话量真要涨到几万条，再考虑自定义表；首版用 CPT 就够，而且能直接复用 WP 原生的列表页、筛选、导出。

### 10.7 安全与限流

| 项 | 做法 |
| --- | --- |
| Key | 只存 `wp_options`，绝不进前端、绝不进 git |
| 限流 | 用 transient 按 IP 计数（如 1 分钟 10 次 / 1 天 200 次） |
| 历史长度 | 只带最近 6 轮进提示词，控住 token 成本 |
| 输出上限 | 设 `maxTokens`，防跑飞 |
| 兜底 | 命中不了知识库 → 留邮箱 + 会话标「待跟进」+ `wp_mail` 通知 |

### 10.8 施工顺序（约 3~4 天）

| 阶段 | 内容 | 工时 |
| --- | --- | --- |
| 1 | 插件骨架 + 设置页 + L1/L2 结构化知识库 + 云端模型 + 本站挂件（模式 2） | 1.5 天 |
| 2 | 后台会话列表与详情 + 兜底邮件 + 限流 | 1 天 |
| 3 | 普通主题站投放（模式 1 `wp_footer` + 短代码） | 0.5 天 |
| 4 | 向量检索 L3（**视效果决定做不做**） | 1 天 |

阶段 1~3 做完就已经是"能跨站复用"的成品；阶段 4 属于可选优化。

### 10.9 明确不选的做法

| 不选 | 原因 |
| --- | --- |
| fork 第三方插件 | 升级断路、许可证风险、维护成本最高 |
| 首版就上向量数据库 / Docker | 数据量根本用不上，白白吃掉 C 盘那点空间 |
| 前端直连模型 | Key 等于公开 |
| 一上来做中央服务 | 站点没几个的时候是过度设计 |
| 首版就做 L3 向量检索 | 结构化匹配先跑起来才知道差在哪 |

### 10.10 一句话选型

**自建独立插件 + 插件侧持 Key + 结构化检索优先（L1/L2）+ OpenAI 兼容的模型层 + 双模式投放（`wp_footer` / 无头 JS）。**

### 11.4 顺手修的问题

1. **检索被虚词凑分误命中**：`你们` 这类 2-gram 能跟任意 FAQ 的 keywords 配上，把"上门安装服务怎么收费"也放进模型。已加 2-gram 虚词表（`site_chat_kb_stopwords()`），复测 12 条问法，无关提问全部归零。
2. **`tools/capture.ps1` 缺 UTF-8 BOM**：PowerShell 5.1 按 ANSI 解析含中文的脚本会报一堆语法错。已补 BOM（符合项目 `.ps1` 约定），并新增 `tools/chat-open-and-ask.js`（纯 ASCII，中文用 `\u` 转义）用于挂件回归验证。
3. **英文站挂件显示中文**（用户实机发现）：中英切换是**客户端路由**，挂件脚本只加载一次、且配置已读进闭包，所以从中文站切到 `/en` 后挂件仍是中文。修法两步——① 挂件脚本重构成「可重建」结构，暴露 `window.SiteChat.reinit(config)`（销毁 DOM / 样式 / 事件监听后按新配置重建，并用 `sessionStorage` 记住面板展开状态）；② 前端 `chat-widget-loader.tsx` 改用 `usePathname()` 判断语言，语言变化时调用 `reinit`。

   实测：`/en` 直接打开 → 英文；点「中文」→ 中文；再点「EN」→ 英文，全程只有 1 个气泡、1 个样式节点（无重复残留）。

   > 已知取舍：重建会清空**界面上**的旧对话气泡（后端沿用同一个 `session_id`，记录不丢）。若要保留界面历史，可在 `reinit` 时向服务端拉取会话已有消息重新渲染。

4. **英文文案原本是单份**：问候语 / 快捷问题 / 提示词 / 兜底话术 / 系统提示词原先只有一份中文。已加 `*_en` 分语言配置（设置页可分别维护，留空回退中文），`/config?locale=en` 返回英文整包。
5. **模型说要转人工、前端却没弹邮箱框**：模型回复"这个问题我需要同事帮您确认…留个邮箱"时 `escalate` 仍是 false，访客看不到留邮箱入口。修法两层——① 提示词加一条"需要同事跟进时在回答末尾单独加一行 `[[转人工]]`"（服务端会剥掉这行，不展示给访客）；② 措辞兜底：回复里出现 `需要同事` / `同事确认` / `need a colleague` 等字样时也置 `escalate`。第一版兜底把"留个邮箱"也算，导致**正常回答**（如"厨房卫浴有哪些地板"）也弹表单，已收窄到"需要人工介入"这一族措辞。
